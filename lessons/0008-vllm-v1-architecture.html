3三个新概念

① 用 token 预算代替「阶段」

这是 vLLM 与 nano-vllm 最根本的差别。vLLM 调度器开头有一段注释[scheduler.py L708–717]，值得逐字读：

“There's no decoding phase nor prefill phase in the scheduler. Each request just has the num_computed_tokens and num_tokens_with_spec. … At each step, the scheduler tries to assign tokens to the requests so that each request's num_computed_tokens can catch up its num_tokens_with_spec.”

翻译过来：每条请求自己有一个「已算 token 数」，调度器每轮只是给它分配一些 token 预算，让它往前追。 于是：

  • chunked prefill 不需要特殊分支——它就是「这轮只追了一部分」。
  • 投机解码不需要特殊分支——num_tokens_with_spec 比实际 token 多几个 draft。
  • 前缀缓存经专门查找与分配路径后，可通过同一进度账本表达——num_computed_tokens 一开始就不是 0。

nano-vllm 的 is_prefill 布尔值，在 vLLM 里被每请求的计数器取代了。这就是「简化版教你概念、生产版给你一般化」的典型例子。

② SchedulerOutput：调度与执行的契约

vllm/v1/core/sched/output.py · L245–class SchedulerOutput:
    scheduled_new_reqs: list[NewRequestData]        # 第一次见到的请求，传完整数据
    scheduled_cached_reqs: CachedRequestData       # 见过的，只传 diff
    num_scheduled_tokens: dict[str, int]           # 每条请求这轮算多少
    total_num_scheduled_tokens: int
    scheduled_spec_decode_tokens: dict[str, list[int]]
    finished_req_ids: set[str]                     # 通知 worker 释放状态

注意 scheduled_new_reqs / scheduled_cached_reqs 的区分：worker 进程里缓存了请求数据，只有新请求才需要传完整字段。这是跨进程通信的成本意识——nano-vllm 用 Sequence.__getstate__ 做的是同一件事，只是更粗暴。

③ 异步：调度不等前向

future = self.model_executor.execute_model(scheduler_output, non_block=True)
...
model_output = self._wait_for_output(future)

提交前向后，主进程立刻继续做别的事（算 grammar bitmask、处理 abort 队列），等结果时再阻塞。这就是 step_with_batch_queue 和 async_scheduling 的基础：CPU 侧的调度与 GPU 侧的计算重叠。

nano-vllm 是严格串行的：run() 返回之前什么都做不了。对 1.5 秒一次 decode 的小模型无所谓，对 7B 以上、每次 decode 几十毫秒的服务，CPU 空转就是浪费。

5为什么要有 EngineCoreProc

单进程版本（EngineCore）已经完整，但生产部署时前端和引擎核通常分进程：

  • 前端要处理 HTTP、序列化、多租户，Python GIL 会被它占住。
  • 引擎核要独占 CPU 循环，不受前端抖动影响。
  • 崩溃隔离：前端挂了不影响正在跑的请求（反之亦然）。

EngineCoreProc[core.py L1299] 因此有一个 run_busy_loop()：不断从输入队列取请求、执行 step、把输出推回队列。这和 nano-vllm 里 worker 的 loop() 思路一致，只是通道从共享内存换成了 ZMQ。
